# Flow-Skill 输入输出契约设计

> 版本：0.2.0 设计稿（待实现）
> 状态：设计定稿，未经实现
> 关联文档：`文件路径契约.md`（路径基准/书写规范/核验规则/数据目录解析链）、`Skill接入说明.md`（V1 行为）、`审批内嵌设计.md`（挂起中，本设计预留衔接点）

---

## 1. 背景与目标

### 1.1 现状问题（0.1.x）

当前任务的输入输出完全隐式：

- `TaskDefinition` 没有 `inputs` / `outputs` 字段，任务需要什么、产出什么没有任何声明；
- 下游 payload 的 `inputs.dependencies` 机械注入全部直接依赖的 outputs，Agent 看到一堆未声明的数据"猜着用"；
- 文件产物只靠 result JSON 里的路径字符串约定，包对路径不解析、不校验——路径越界、文件不存在、格式不对全部畅通无阻；
- validator 被迫承担大量样板检查（文件存在、类型 isinstance），业务逻辑与协议检查混在一起；
- 接口契约最好情况写在 instruction 的自然语言里，与 validator 代码两处定义、容易不一致。

### 1.2 目标

任务声明式定义输入输出契约，契约在三处生效：

```text
定义期（Flow 加载）  → 契约错误当场报错，跑不起来的流程不存在
领取期（get_next_task）→ 按声明装配输入，Agent 只看到该看的东西
提交期（submit_task_result）→ 按声明核验输出，不合格就 reject
```

### 1.3 不变式（全程约束）

- 包保持**零第三方依赖**：所有包级核验只用标准库（文件存在性用 `Path.exists()`，xlsx sheet 清单用 `zipfile` + ElementTree 读 `xl/workbook.xml`，md/html 用文本读取）；
- **状态机不加任何状态**：契约核验失败走现有 `rejected` 通道，输入不可用走现有 `waiting` 通道；仅新增两条**转换**（状态集合不变）：`PENDING → FAILED`（校验重试耗尽）、`RUNNING → FAILED`（提交被拒重试耗尽，复用现有转换）；
- 不声明 inputs/outputs 的任务行为与 0.1.x 完全一致（向后兼容，同一流程可混用）。

## 2. API：Input 三类

### 2.1 TextInput — 静态/短文本输入

```python
TextInput(
    name="note",              # 必填：payload 键名，任务内唯一
    value="仅统计华东区域",     # 静态文本（与 source 互斥）
    source="run_inputs",      # 可选：从 Run 输入取字符串字段
    key="备注",                # source 时指定字段
    required=True,            # 默认 True
)
```

- 核验：值必须是字符串，**绝不按路径解析**；
- 定义期校验：`value` 与 `source` 同时给 → 报错。

### 2.2 JsonInput — 结构化输入

```python
JsonInput(
    name="budget",            # 必填
    source="run_inputs",      # 或 "other_task"
    from_task="load_budget",  # source="other_task" 时必填
    key="items",              # 可选：取来源对象的某字段
    required=True,
    schema={...},             # 可选：输入侧 JSON Schema（复用 Output 的引擎）
)
```

- 核验：值必须是 dict/list/数字，**字符串报错**（防歧义：字符串一律走 FileInput）；
- 定义期校验：声明 `sheet` / `format` → 报错（语义错位）。

### 2.3 FileInput — 文件输入

```python
FileInput(
    name="sales",             # 必填（name = 逻辑数据单元，不是物理文件名）
    from_task="collect",      # 必填（文件必然来自上游任务）
    output="workbook",        # 可选：引用上游 Output 的 name（见下"多文件输出歧义"）
    format=["xlsx"],          # 默认 ["xlsx", "csv", "md", "html"]
    sheet="collect__明细",     # 单数：指定工作簿里的一张子表
    sheets=["collect__明细", "collect__汇总"],   # 复数：整包订阅多张子表（与 sheet 互斥）
    required=True,
)
```

- 装配：上游提交的路径解析为 **workspace 内绝对路径**注入，附 `name_meta`（kind / format / sheets 清单，含上游声明的行数等信息）；
- 核验：扩展名 ∈ format、文件存在；`sheet` / `sheets` 指定时定义期校验前缀归属（必须属于 from_task 的前缀）且逐张存在于上游声明的 sheets 契约内。

**多文件输出歧义**：上游声明了多个文件输出时，`output` 必填，缺失或名字不存在 → 定义期报错；上游只有一个文件输出 → 可省略，自动指向它。`output` 引用的是上游声明的 Output name（契约对契约），上游内部路径/布局变化不影响下游。

**多子表两种写法的选择标准**：下游任务语义是"处理某张表" → 拆单（`sheet=` 单数，name 即语义，数据面收窄）；语义是"面对整本工作簿"（联合多表分析、渲染全部产物）→ 整包（`sheets=[...]` 或省略，meta 给全貌）。同一任务内两种写法可混用。

### 2.4 公共规则

| 规则 | 说明 |
|---|---|
| name 唯一 | 同一任务内 Input name 重复 → 定义期报错 |
| from_task 存在性 | 引用不存在的任务 → 定义期报错 |
| output 引用合法性 | from_task 有多个文件输出而未指定 output → 定义期报错；指定的 output 名不存在 → 定义期报错 |
| required 装配失败 | 见 §5.4 校验重试与失败（来源被跳过 → 级联跳过；其他失败 → 重试后失败） |
| **数据依赖 ⊆ 执行依赖** | 声明式输入的 `from_task` 必须同时出现在任务的 `after` 中，否则**定义期报错**。理由：调度门禁、装配时序、审批 stop 级联跳过的收集范围全部沿 after 依赖边工作；数据依赖游离在依赖边外会导致"来源未完成就被领取 → 装配空转重试"和"stop 漏跳过数据依赖者"两个洞 |
| 来源三选一 | `run_inputs` / `other_task`（带 from_task）/ 静态 value；组合非法 → 定义期报错。另有 `review` 来源（审批内嵌设计的返工意见，见 `审批内嵌设计.md` §6） |

**human 任务同样支持 inputs/outputs**：inputs 用于把待审任务的输出装配进审核场景（如 FileInput 引入待审产物路径）；outputs 声明用户提交的结构（`user_decision` 用 `JsonOutput(schema={"decision": ...})` 管住）。同时收紧历史遗留的 P2 漏洞：`mode="approval"` 的 human 任务**只接受 `user_decision`**，`mode="input"` 只接受 `user_input`，混用 → 提交被拒。

**name 的定位**：name 是任务之间契约的"地址系统"——回答"是什么"（逻辑数据单元），from_task/output/path/sheet 回答"从哪来、在哪"（实现细节）。上游内部路径、文件名、sheet 布局变化不影响下游，只要契约 name 稳定。payload 拍平、错误定位、schema/meta 挂载全部以 name 为键。

## 3. API：Output 两类

> 定稿说明：Output 端收敛为两类——JsonOutput（schema 契约）与统一 FileOutput（path/format/metadata 三要素，格式差异收进 metadata）。不再为 Excel/Markdown/HTML 设独立构造器，核验按 format 值查表分发。

### 3.1 JsonOutput

```python
JsonOutput(
    name="summary",
    schema={                       # 可选：JSON Schema 内置子集（见 §6）
        "type": "object",
        "properties": {
            "total":  {"type": "integer", "minimum": 0},
            "region": {"type": "string", "enum": ["华东", "华南", "华北"]},
        },
        "required": ["total", "region"],
    },
    # 或简写（内部翻译成等价 schema，与 schema 互斥）：
    # required={"total": int, "region": str}, optional={"note": str}
)
```

### 3.2 FileOutput — 统一文件输出

```python
FileOutput(
    name="workbook",              # 必填
    path="outputs/run.xlsx",      # 必填：相对 Run Workspace 的路径
    format="xlsx",                # 必填：xlsx / csv / md / html / pdf / ...
    metadata={...},               # 可选：格式相关的契约参数（见下表）
)
```

**metadata 按 format 分发**，键与 format 不匹配 → 定义期报错：

| format | metadata 支持的键 | 包级核验（零依赖） |
|---|---|---|
| `xlsx` | `sheets: [名 或 {name, min_rows}]` | zipfile 读 `xl/workbook.xml`：sheet 存在性、`<task_id>__` 前缀所有权、无孤儿 sheet |
| `md` | `headings: [...]`、`min_chars: n` | 标题行按序出现、篇幅下限 |
| `html` | `contains: [...]`、`min_chars: n` | 片段包含、篇幅下限 |
| 其他（csv/pdf/…） | ——（给了非空 metadata 即报错） | 仅路径 + 扩展名 + 存在性 |

**必填参数**：`name` / `path` / `format`。

### 3.3 Excel 单工作簿模式（sheet 契约）

多个任务的 FileOutput 指向**同一个工作簿**（如 `outputs/run.xlsx`），以 sheet 划分所有权：

```text
命名：sheet = <task_id>__<子表名>，如 collect__明细、analyze__异常标记
所有权：本任务前缀的 sheet 可写，其他前缀只读
孤儿检查：工作簿里出现不属于任何已声明任务的 sheet → 提交被拒
返工清场：返工重跑时，任务先删除自己前缀的全部旧 sheet 再重新生成（validator 模板提供检查）
命名限制：sheet 名 ≤31 字符且不含 : \ / ? * [ ]；建议 task_id ≤10 字符、子表名 ≤15 字符
```

时序保证：串行执行 + 上游 confirmed 后才放行下游 → 下游读到的上游 sheet 一定是终版，无并发写风险。

## 4. 内部归一（构造器是糖）

三个 Input 构造器与两个 Output 构造器分别归一为两个内部结构存库：

```python
InputSpec(
    kind: "text" | "json" | "file",
    name: str,
    source: "run_inputs" | "other_task" | "static" | "review" | None,
    from_task: str | None,
    output: str | None,         # file 专用：引用上游 Output 的 name
    key: str | None,
    required: bool,
    value: str | None,          # text 专用
    format: tuple[str, ...],    # file 专用
    sheet: str | None,          # file 专用（单表订阅）
    sheets: tuple[str, ...],    # file 专用（整包订阅，与 sheet 互斥）
    schema: dict | None,        # json 可选（输入侧）
)

OutputSpec(
    kind: "json" | "file",
    name: str,
    schema: dict | None,        # json 专用
    path: str | None,           # file 专用
    format: str | None,         # file 专用
    metadata: dict | None,      # file 专用（sheets / headings / contains / min_chars）
)
```

存储与调度器只处理 spec，按 `kind` / `format` 分发核验逻辑（查表函数，便于测试）。

## 5. 运行时行为

### 5.1 领取期：payload 装配

声明了 inputs 的任务，payload 的 inputs **按声明拍平**：

```json
{
  "status": "task_ready",
  "run_id": "run_x",
  "task": {
    "task_id": "analyze",
    "task_status": "running",
    "type": "agent",
    "instruction": "C:\\skills\\shop-report\\tasks\\analyze.md",
    "inputs": {
      "params": {"start": "2026-11-01", "end": "2026-11-21"},
      "sales": "C:\\...\\runs\\run_x\\outputs\\run.xlsx",
      "sales_meta": {"kind": "file", "format": "xlsx", "sheets": ["collect__明细"]},
      "budget": {"total": 50000, "items": []},
      "note": "仅统计华东区域"
    },
    "outputs_spec": [
      {"name": "workbook", "kind": "file", "format": "xlsx",
       "path": "outputs/run.xlsx",
       "metadata": {"sheets": ["collect__明细", "collect__汇总"]}},
      {"name": "summary", "kind": "json", "schema": {"...": "..."}}
    ],
    "workspace": {"root": "...", "inputs": "...", "working": "...", "outputs": "..."},
    "metadata": {"name": "销售分析"}
  }
}
```

要点：

- **inputs 拍平**：每个 Input 以 name 为键直接出现在 `inputs` 里（去掉旧 `run/task/dependencies` 分类层，未声明的数据不进 payload）；FileInput 注入绝对路径 + `name_meta`（kind/format/sheets，只有文件输入带 meta——路径是纯净可直用的值，说明信息放旁边）；JsonInput 注入结构；TextInput 注入文本；
- **outputs_spec 随 payload 下发**：提交契约对 Agent 每次可见，不依赖跨会话记忆；
- instruction 绝对路径化（配合 Flow `base_dir`，见 §8）。

### 5.2 提交期：核验管线

```text
① 静态检查     result_type 合法？任务状态允许提交？（否则抛异常）
② 契约核验     按 outputs_spec 逐项：
                JsonOutput  → name 存在 → 值是结构化 → schema 校验
                FileOutput  → name 存在 → 路径在 workspace 内 → 扩展名=format
                              → 文件存在 → 按 format 分发 metadata 核验
                任一不过 → 记 task_result_rejected 事件，返回 rejected
                              （重试上限见 §5.4）
③ 业务 validator（如有）→ 内容语义检查，不过同样 rejected（任务保持 running）
④ 全部通过 → 任务 completed，result 整体存 outputs_json，Run 置 running
              返回 {status: "accepted", next_available: true}
```

rejected 响应的 errors 带 `输出名.字段名` 前缀，Agent 可直接照着修正重提：

```json
{"status": "rejected",
 "errors": ["summary.total 缺失", "workbook 缺少声明 sheet: collect__汇总"]}
```

### 5.3 契约核验与 validator 的分工

| 层 | 管什么 | 谁写 |
|---|---|---|
| 契约核验（②） | 协议级：键存在、类型、文件存在、sheet 结构、标题结构 | 声明自动生成，包执行，**绕不过** |
| validator（③） | 语义级：数值范围、枚举、跨字段一致性、单元格内容 | 作者写（可选） |
| when | 任务跳不跳过（另一机制，与校验无关） | 作者写 |

**声明了 Output 后，简单任务可以不写 validator**——原来 validator 里 80% 的样板检查（存在性、路径、类型）由声明承担，validator 降级为"有业务语义才写"。

### 5.4 校验重试与失败

**重试闭环的核心：错误信息必须回流给 AI。** 每次校验失败产生的 errors 都要送达下一个执行者——提交期的 rejected 响应、装配期失败后的任务 payload——AI 依据 errors 修正，重试才有意义；只计数不给错误信息的重试是盲目的。

**提交被拒（rejected）有重试上限**。任务定义增加 `max_validation_retries`（默认 3，0 表示一次都不允许重试）：

```text
提交 → 契约核验/validator 不过 → 任务保持 running，retry_count 不变，
      返回 rejected + errors（完整错误清单，Agent 依据它修正后重新提交）
累计被拒次数达到 max_validation_retries：
      → 任务 RUNNING → FAILED（事件 task_failed，reason="validation_retries_exhausted"）
      → Run 随之 failed
```

错误回流的两条通道：

```text
① 同会话重试：rejected 响应的 errors 数组当场返回给提交的 Agent，
   它读错误 → 修正 → 立即重新提交（最常见路径）

② 跨会话回流：任务的 payload 新增两个字段——
   "validation_retry_count": 2,
   "last_validation_errors": ["summary.total 缺失", "workbook 缺少 sheet: ..."]
   Agent 重新领取任务（如 stale 恢复、新会话续跑）时，能看到此前失败的
   全部原因，避免重蹈覆辙；instruction 模板要求 Agent 优先按
   last_validation_errors 修正
```

**required 输入装配失败的分流**（装配发生在领取期写事务内）：

```text
来源任务被 skipped（结构性的，永远不会产出）
      → 下游任务自动级联跳过：PENDING → SKIPPED
         事件 task_skipped, reason="required_input_skipped"，流程继续走完

其他装配失败（来源 completed 但没产出对应内容、输入侧 schema 不满足等，
      属于契约违背/作者错误）
      → 任务进入重试：保持 PENDING，validation_retry_count +1，
         记事件 input_validation_failed（含具体错误，进入 last_validation_errors）；
         重新调度时再次尝试装配，Agent 从 payload 的 last_validation_errors
         得知此前失败原因
      → 重试次数达到 max_validation_retries → 任务 PENDING → FAILED，
         Run failed，错误信息指明具体违背的契约项
```

设计意图：**给人工干预留窗口**——重试期间用户可以修正上游产物或 abort Run，而不是一失败就死锁（干等）或一失败就全断（直接 failed）。重试在写事务内只做装配和计数，不阻塞调度。

## 6. JSON Schema 内置子集校验器

包零依赖，不引入 jsonschema 库。内置支持的关键字：

```text
type（object/array/string/number/integer/boolean/null）
properties / required / items
enum / minimum / maximum / minLength / maxLength / minItems
additionalProperties: false
```

- **不支持的关键字**（$ref、allOf、patternProperties、format 等）在**定义期报错**——宁可流程起不来，不做静默忽略；
- **可选增强**：环境装了 jsonschema 库时自动用它做全量校验；默认只承诺内置子集，保证有库/无库行为一致；
- 使用纪律：schema 用于摘要类输出（几十字段量级）；大明细数据走 FileOutput，schema 校验跑在写事务内，复杂 schema 会拖慢调度。

## 7. 兼容与迁移

| 场景 | 行为 |
|---|---|
| 任务不声明 inputs | payload 维持现状：`inputs: {run, task, dependencies}` 三层嵌套 |
| 任务不声明 outputs | 提交不核验，仅走 validator（现状） |
| 同一流程混用 | 支持，按任务各自有无声明区分 |
| 旧 Run 恢复 | spec 随 Run 快照存库，旧库新列默认空 → 走现状逻辑 |

## 8. 关联设计（本设计依赖/衔接）

- **Flow `base_dir`**：instruction 相对路径基于 workflow.py 所在目录解析为绝对路径（解决 CWD 漂移）；
- **ctx.resolve / is_within_workspace**：validator 深度检查的工具（本设计实现）；
- **文件路径契约（`文件路径契约.md`）**：三类基准目录、workspace 路径书写规范与核验、instruction 的 base_dir 解析、data_dir 注册表/--rebind/技能指纹、ctx.resolve 语义——本设计中 path 相关规则均以其为准；
- **审批内嵌（挂起中）**：审核展示可直接消费 FileOutput 声明的产物；human 节点也可用 inputs 声明待审任务的输出。

## 9. 实现清单

```text
models.py       InputSpec / OutputSpec / 五个构造器 + 定义期参数校验
schema.py       新增：JSON Schema 内置子集校验器 + 文件契约核验器
                （zip sheet 清单 / md 标题 / html 片段），约 200 行
workflow.py     agent/human 加 inputs/outputs 参数；TaskDefinition 加
                max_validation_retries（默认 3）；Flow.base_dir；
                定义期契约校验（引用存在性、output 指向、前缀归属、path 越界、参数互斥）；
                human 任务 mode/result_type 收紧（approval 只收 user_decision）
state.py        TASK_TRANSITIONS 新增 PENDING → FAILED（校验重试耗尽）
scheduler.py    领取期装配（inputs 拍平 + name_meta + outputs_spec + 
                last_validation_errors / validation_retry_count 回流）；
                级联跳过（required 来源被 skipped → 任务 SKIPPED）；
```

## 10. 测试场景清单

1. **定义期**：非法参数组合（value+source、json 带 sheet、format 与 metadata 键不匹配、sheet 与 sheets 互斥）、from_task 不存在、output 引用缺失/不存在、path 越界、sheet 前缀不归属 → 全部加载即报错；
2. **装配期**：JsonInput/FileInput/TextInput 各来源装配正确；多文件输出的 output 指向正确；多子表整包与拆单两种写法装配一致；required 来源被 skipped → 级联跳过；装配失败重试计数、错误回流（payload 携带 last_validation_errors）与耗尽转 FAILED；
3. **提交期**：JsonOutput schema 通过/拒绝；FileOutput 各 format 的 metadata 核验；xlsx 孤儿 sheet 拦截；文件不存在拦截；**被拒重试上限**（连续 rejected 达 max_validation_retries → 任务和 Run 失败）与错误回流（rejected 响应 errors 完整）；human 任务 mode 与 result_type 收紧；
4. **兼容**：未声明任务走旧 payload 形态；旧库（无新列）恢复不报错；
5. **端到端**：三任务流程（collect 产 Excel → analyze 读 sheet → report 产 md），契约全程生效，validator 只写业务逻辑。
