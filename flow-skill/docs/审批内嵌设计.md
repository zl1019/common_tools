# 审批内嵌任务状态机（requires_approval）设计文档

状态：已评审待实现
版本目标：flow-skill 0.2.0
日期：2026-11-21

## 1. 背景与目标

当前"任务执行完要人审核"必须成对定义节点：agent 任务后面手工挂一个
`mode="approval"` 的 human 节点。当多数任务都需要审核时，流程定义和流程图显著变长。

本设计把"审核"内嵌为 agent 任务自身的一个生命周期阶段。作者只需：

```python
flow.agent(
    id="collect",
    instruction="tasks/collect.md",
    validator=validate_collect,
    requires_approval=True,   # 新增：执行结果须经用户审核
    max_rework=2,             # 新增：审核拒绝后的返工次数上限，默认 2
)
```

下游任务照常写 `after="collect"`，自动被审核门禁挡住，无需感知审核细节。

### 1.1 与 human 节点的分工

human 节点保留，职责收窄为两类：

| 需求 | 用法 | 说明 |
|---|---|---|
| 任务执行结果审核 | `flow.agent(..., requires_approval=True)` | 本设计新增，替代"agent+approval 成对节点" |
| 向用户询问参数/输入 | `flow.human(mode="input")` | 保留不变，如流程开头收集参数 |
| 不绑定任务的独立决策点 | `flow.human(mode="approval")` | 保留，向后兼容 |

## 2. 状态机变更

新增两个持久化任务状态：

- `awaiting_review`：validator 已通过、执行结果已保存，等待用户审核；
- `confirmed`：用户审核通过（或选择结束），终态。

返工不新增持久化状态，直接回到 `pending` 并注入审核意见。

`TASK_TRANSITIONS` 增量：

```text
RUNNING          → { AWAITING_REVIEW }                      （新增）
AWAITING_REVIEW  → { CONFIRMED, PENDING, FAILED }           （新增）
```

终态集合变更：

```python
TERMINAL_TASK_STATUSES = {COMPLETED, CONFIRMED, SKIPPED}
```

`awaiting_review` 不是终态，下游依赖自然无法满足，这是审核门禁的实现方式，
下游任务不需要写任何 `when` 条件。

### 2.1 stale 豁免

`awaiting_review` 不参与 `stale_after` 检查：等人审核没有时限，与遗留执行
是两回事。`is_stale()` 只对 `running` 状态生效，此语义不变。

## 3. 审核决定协议

`awaiting_review` 状态的任务通过 `submit-task-result --result-type user_decision`
提交审核决定，`result` 为 JSON 对象，支持三种决定：

| decision | 含义 | 行为 |
|---|---|---|
| `approve` | 通过 | 任务 → `confirmed`，下游照常调度 |
| `stop` | 结束 | 任务 → `confirmed`（记录 stop），其全部下游任务级联 SKIPPED，Run 正常走完成门禁后 `completed`。语义："当前产物即为最终交付" |
| `rework` | 修改意见返工 | 任务 → `pending` 重跑，`review_count+1`；`comment` 必填（作为修改意见注入重跑） |

约束：

- `rework` 提交缺少 `comment` → 返回 `rejected`，错误信息要求补充意见；
- `review_count >= max_rework` 时再提交 `rework` → 任务直接 `failed`，Run 随之 `failed`，响应中说明返工次数耗尽；
- 其余 decision 值 → 返回 `rejected`，列出允许的三种取值；
- 不需要单独的 `abort`：放弃流程等同 `stop`（正常收尾）或由用户直接放弃对话。

## 4. 数据模型变更

`workflow_tasks` 表新增列（均带默认值，旧库通过 `ALTER TABLE` 幂等迁移）：

```sql
requires_approval INTEGER NOT NULL DEFAULT 0;
review_count      INTEGER NOT NULL DEFAULT 0;
max_rework        INTEGER NOT NULL DEFAULT 0;
review_json       TEXT;              -- 最近一次审核决定 {"decision":..,"comment":..}
```

字段语义：

- `started_at`：本次执行的开始时间；返工重跑时清空重写；
- `finished_at`：进入 `confirmed` / `completed` / `failed` / `skipped` 时写入；
- `outputs_json`：始终存放执行结果（validator 通过的那份），审核决定只进 `review_json`，
  两者不混存，`ctx.output()` 语义不变。

## 5. 调度行为变更

### 5.1 get_next_task

`_active_task_response` 增加一个分支：发现 `awaiting_review` 任务 → 返回
`waiting_user`，`reason="task_review_required"`，`task` payload 包含：

```json
{
  "task_id": "collect",
  "task_status": "awaiting_review",
  "type": "agent",
  "instruction": "C:\\skills\\shop-report\\tasks\\collect.md",
  "outputs": { "...": "执行结果 JSON，供审核人查看；文件输出的路径为解析后的 workspace 内绝对路径" },
  "review_count": 0,
  "max_rework": 2,
  "review_prompt": "任务 collect 已完成执行并通过校验，等待审核：approve / stop / rework"
}
```

执行结果必须随响应返回，Agent 才能向用户展示待审核内容。

### 5.2 submit_task_result

按任务当前状态分发，增量如下：

```text
RUNNING + execution_result:
    validator 通过
      → requires_approval=True → 转 AWAITING_REVIEW，返回 SUBMITTED_FOR_REVIEW
      → requires_approval=False → 照旧 COMPLETED，返回 ACCEPTED

AWAITING_REVIEW + user_decision:
    approve → CONFIRMED（finished_at 写入）
    stop    → CONFIRMED + 级联 SKIPPED 全部传递下游任务
    rework  → review_count < max_rework：
                  转 PENDING，event 注入 comment，返回 RETRY_SCHEDULED
              review_count >= max_rework：
                  转 FAILED，Run → FAILED，返回 RUN_FAILED

其他组合 → InvalidStateError（与现状一致）

核验管线归属：`awaiting_review + user_decision` 只走审核协议核验
（decision ∈ {approve, stop, rework}，rework 必带 comment），
**不执行** outputs_spec 契约核验与 validator——两者已在任务转
awaiting_review 前完成并落库。0.2.0 提交管线按任务状态分发时，
此分支跳过 ②③ 层（见输入输出契约设计 §5.2）。
```

级联跳过实现：以被 stop 的任务为根，沿依赖边正向收集全部（传递）下游任务，
把其中所有非终态任务逐个转 `SKIPPED`，事件 reason 均为 `review_stop`。

### 5.3 TaskContext

```python
ctx.output("collect")            # 不变：执行结果
ctx.review("collect")            # 新增：{"decision": ..., "comment": ...}，未审核为 None
```

`completion_gate` 把 `confirmed` 视为已完成任务，取数仍用 `ctx.output()`。

## 6. 返工时的输入注入（适配 0.2.0 声明式 payload）

返工重跑后，审核意见作为**顶层保留键 `inputs.review`** 自动注入，两种 payload 形态一致：

```text
未声明 inputs 的任务（旧形态，inputs = {run, task, dependencies}）：
  "inputs": {"run": {}, "task": {}, "dependencies": {},
             "review": {"comment": "第3列汇总口径不对", "review_count": 1}}

声明了 inputs 的任务（拍平形态）：
  "inputs": {"params": {...}, ..., "review": {...}}
```

可选显式声明：任务可声明 `JsonInput(name="review", source="review")`（输入来源新增
`review`，见输入输出契约设计 §2.4），以便挂 schema 校验或控制 required 语义；
声明与自动注入并存时，声明优先。

Task 说明文件应要求 Agent 读取 `inputs.review.comment` 并针对性修正；
`review_count` 供 Agent 在结果中标注这是第几次返工版本。
同时按文件路径契约的 Excel 清场规则：返工重跑须先删除自己前缀的旧 sheet
再重新生成（validator 模板提供检查）。

## 7. 事件流

```text
task_started
task_executed                    （validator 通过，转 awaiting_review）
task_review_approved             （含 comment、review_count）
task_review_stopped              （stop 决定）
task_review_rejected             （含 comment、review_count）
task_rework_scheduled            （转 pending，含 comment）
task_rework_exhausted            （返工次数耗尽，转 failed）
task_confirmed
task_skipped (reason=review_stop)
run_status_changed
```

"谁执行、谁审核"通过 `task_executed` 与 `task_review_*` 事件天然分离，审计语义
不弱于两节点模式。

## 8. 定义期校验（Flow.validate）

- `requires_approval=True` 的任务必须是 agent 类型（human 任务不允许该参数）；
- agent 任务必须有 validator（既有规则，不变）；
- `max_rework >= 0`；
- `SAFE_ID` 等既有校验不变。

## 9. CLI 变更

无新增子命令。审核提交复用现有命令：

```text
python workflow.py submit-task-result --run-id R --task-id collect \
  --result-type user_decision --result-json '{"decision":"approve"}' --data-dir D
```

## 10. 兼容性与迁移

- 两节点写法（agent + human approval）继续完全支持，新老写法可在同一 Flow 共存；
- `Storage.initialize()` 检查 `workflow_tasks` 既有列，缺列则 `ALTER TABLE ADD COLUMN`；
- `requires_approval` 属于定义期属性，随 Run 快照落库；旧 Run 恢复时按创建时快照执行，
  与 Flow 版本校验机制一致；
- 不兼容点：`RUNNING` 任务 validator 通过后若定义了 `requires_approval`，其响应
  从 `accepted` 变为 `submitted_for_review`——接入文档 §8.3 需同步说明。

## 12. 已确认的设计决策

- 拒绝行为：三选决定（approve / stop / rework），由用户于 2026-11-21 确认；
- human 节点保留：`mode="input"`（询问参数）与独立 `mode="approval"` 不受影响；
- 自动失败重试保持关闭状态（0.1.x 决定不变）；
- 遗留任务的用户手动 retry（stale 恢复）保持不变。

## 13. 2026-11-23 复审：与 0.2.0 契约设计的衔接

复审结论：核心状态机设计成立（awaiting_review 门禁、三选决定、rework 注入、
stale 豁免均与调度机制自洽）。与已定稿的《输入输出契约设计》《文件路径契约》
存在五处交界问题，修正如下：

1. **数据依赖必须包含于执行依赖**（已同步补进输入输出契约 §2.4）：
   声明式输入的 `from_task` 必须出现在任务的 `after` 中，定义期强制。
   门禁、装配时序、stop 级联跳过的收集范围全部沿 after 依赖边工作；
   数据依赖游离在依赖边外会造成"来源未完成就被领取 → 装配空转重试"
   和"stop 漏跳过数据依赖者"两个洞。此规则落地后依赖图完整，问题消解。

2. **awaiting_review 提交的核验管线归属**（§5.2 已补）：只走审核协议核验，
   不执行 outputs_spec 契约核验与 validator。

3. **rework 意见注入适配声明式 payload**（§6 已改写）：两种形态都自动注入
   顶层保留键 `inputs.review`；可选显式声明 `source="review"` 的 JsonInput。

4. **两套审核词汇并存，文档必须区分**：内嵌审核 `approve/stop/rework` 与
   独立 human approval 节点 `approve/reject` 不强行统一（向后兼容 0.1.x）。
   human approval 的 reject 若要表达"结束"，靠下游任务自带 `when` 条件实现，
   与内嵌审核的 stop（自动级联跳过）语义不同。SKILL 模板分节写清两种场景
   的提交格式，防止 Agent 混用。

5. **双计数澄清**：`max_validation_retries`（提交被拒的重试上限，输入输出
   契约 §5.4）与 `max_rework`（审核返工上限）是两个独立计数、独立上限，
   事件分别记录；SKILL 模板分节说明。
